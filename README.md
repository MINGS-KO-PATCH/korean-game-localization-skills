# Korean Game Localization Skills

실제 게임 한글화 작업에서 확인한 바이너리 구조와 대사 확장 규칙을 Codex가 재사용할 수 있도록 정리한 공개 스킬 저장소입니다.

현재 공개 스킬은 **`game-dialogue-expansion`**입니다. 단순히 문자열을 찾는 데서 끝나지 않고, 번역문이 원문보다 길거나 짧아졌을 때 어떤 길이값·오프셋·포인터·상위 컨테이너를 다시 계산해야 하는지 판정합니다.

## 이 스킬이 해결하는 문제

게임에서 문자가 보인다고 해서 대사를 안전하게 확장할 수 있는 것은 아닙니다. 문자열 길이가 바뀌면 다음 데이터의 위치, 포인터 테이블, 블록 크기, 압축 멤버와 상위 아카이브까지 영향을 받을 수 있습니다.

이 스킬은 대량 대사 추출보다 먼저 다음 질문에 답합니다.

- 대사의 실제 경계는 길이값, 종료자, 다음 포인터 중 무엇이 결정하는가?
- 앞의 숫자는 ID인가, 길이인가, 상대 오프셋인가, 절대 주소인가?
- 대사 하나가 길어지면 어떤 값들이 함께 이동하는가?
- 파일 내부 확장만으로 충분한가, 상위 컨테이너와 로드 버퍼도 바뀌어야 하는가?
- 무수정 왕복과 한 항목 확장 시험으로 구조를 검증했는가?

## 실행 원칙: 추출 전에 확장 가능성부터 판정

`$game-dialogue-expansion`을 호출하면 먼저 확장 가능성 게이트를 수행합니다.

```text
바이너리 구조 조사
      ↓
엔트리 모집단과 경계 기준 확인
      ↓
길이 변화의 전파 범위 계산
      ↓
무수정 추출→재삽입 왕복 검증
      ↓
대표 대사 1개의 증가·감소 시험
      ↓
EXPANDABLE / CONDITIONAL / NOT YET ESTABLISHED
      ↓
안전 범위가 확인된 뒤 대량 추출
```

- **`EXPANDABLE`**: 모집단, 재계산 공식, 용량, 빌드 및 검증 경로가 확인됨
- **`CONDITIONAL`**: 정해진 범위에서는 가능하지만 예외·용량·컨테이너·런타임 조건이 남음
- **`NOT YET ESTABLISHED`**: 문자는 추출되지만 길이를 바꾸는 재삽입 안전성이 아직 증명되지 않음

## 지원하는 대사 확장 구조

| Type | 구조 | 읽는 기준 | 길이가 바뀔 때 |
|---|---|---|---|
| 1 | 1바이트 길이접두 스트림 | `[len:u8][text:len]` 반복 | 해당 `len`을 다시 쓰고 블록 용량 확인 |
| 2 | 2바이트 누적 오프셋 | 텍스트 영역 기준 다음 문자열 시작 | 이후 누적값과 전체 텍스트 크기 재계산 |
| 3 | 4바이트 절대 오프셋 | 파일 시작 기준 각 문자열 시작 | 이후 모든 절대 시작 위치 재계산 |
| 4 | 바깥 절대 + 내부 상대 오프셋 | 파일 기준 블록과 블록 기준 하위 필드 | 내부 상대값과 이후 외부 블록 시작 모두 재계산 |
| 5 | Lua 5.1 4바이트 길이접두 | `size = payload bytes + 종료 00` | 해당 문자열의 `u32le size` 재계산 |
| 6 | 2단 섹션 디렉터리, 잠정 | 섹션 절대 시작 + 섹션 내부 상대 대상 | 섹션 크기·시작·모든 내부 상대값 재계산 |
| 7 | 4바이트 ID + 누적 길이, 잠정 | 원본 ID와 텍스트 영역 기준 누적 끝 | ID·순서는 보존하고 이후 누적값 재계산 |
| 8 | 불규칙 순서 4바이트 누적 참조, 잠정 | 각 슬롯이 가리키는 텍스트 누적 경계 | 슬롯 순서·대상 관계를 보존하고 대상의 새 누적값 기록 |

## Type별 판독 방법

### Type 1 — 1바이트 길이접두

```text
[len:1][text:len][len:1][text:len]...
```

현재 위치에서 길이 한 바이트를 읽고 `1 + len`만큼 이동하는 동작이 여러 레코드에서 연속으로 맞는지 확인합니다. 별도 포인터 테이블은 없습니다. 한 문자열은 최대 255바이트이며 전체 직렬화 결과는 고정 블록 용량을 넘을 수 없습니다.

### Type 2 — 2바이트 누적 오프셋

```text
[헤더][u16le 누적값 × (문자열 수-1)][널종료 문자열 영역]
```

누적값은 텍스트 영역 시작을 0으로 보며 각 다음 문자열의 시작을 나타냅니다. 테이블이 단조 증가하고, 실제 문자열 길이의 누적합 및 헤더의 텍스트 크기와 일치하는지 확인합니다.

### Type 3 — 4바이트 절대 오프셋

```text
[count:u32le][file-absolute start:u32le × count][문자열]
```

`4 + count×4`가 첫 시작값과 일치하는지 확인합니다. 값은 비감소일 수 있으며 같은 값이 반복되면 빈 문자열 또는 공유 참조일 수 있습니다. 종료자 검색이 아니라 포인터 테이블을 모집단 기준으로 사용합니다.

### Type 4 — 중첩 오프셋

```text
[바깥 블록 절대 시작]
  └─ [내부 필드 상대 시작][고정 메타데이터][여러 텍스트 필드]
```

바깥 테이블로 블록을 자른 뒤, 블록 앞의 작은 상대값이 실제 하위 필드 경계와 일치하는지 확인합니다. 번역 시 두 계층을 모두 다시 계산하고 고정 메타데이터는 보존합니다.

### Type 5 — Lua 5.1 4바이트 길이접두

```text
[문자열 태그가 있을 수 있음][size:u32le][payload][00]
size = len(payload) + 1
```

Lua 바이너리 헤더와 `size_t=4`를 확인한 뒤 여러 문자열에서 저장값이 본문 바이트 수+널 한 바이트와 일치하는지 대조합니다. 이 값은 오프셋이 아니라 길이입니다.

### Type 6 — 2단 섹션 오프셋 (잠정)

```text
[section_count]
[identifier:u16][section_size:u16][section_absolute_start:u32]...

section:
[pointer_count:u32][section_relative_target:u32]...
```

섹션 시작·크기와 모든 내부 대상이 선언 범위에 있는지 확인합니다. 대사가 바뀌면 누적 변화량으로 섹션 시작, 섹션 크기, 모든 내부 상대값을 원본 기준에서 재계산합니다. 현재 파일별 명령 내부 참조와 실기 검증 개선사항이 있어 잠정 타입입니다.

### Type 7 — 4바이트 ID + 4바이트 누적 길이 (잠정)

```text
[text_id:u32le][cumulative_end:u32le]...
```

첫 값은 순번처럼 보여도 문자열 ID로 취급합니다.

- **7-A 연속 ID형:** `1, 2, 3...`
- **7-B 불규칙 ID형:** `1–31, 50, 1000...`

두 번째 값은 텍스트 영역 기준 누적 끝 위치입니다. 원본 ID와 엔트리 순서를 그대로 보존하고 번역문 바이트 길이로 누적값만 다시 계산합니다. `raw_count`, 마지막 문자열, 비색인 꼬리와 패딩의 의미는 파일 변형별로 추가 검증합니다.

### Type 8 — 불규칙 순서 4바이트 누적 참조 (잠정)

```text
slot[j]:u32le = cumulative_end[target_index[j]]
```

4바이트 슬롯만 연속되며 별도 ID가 붙지 않습니다. 슬롯의 저장 순서는 대사 순서가 아니라 게임의 참조 순서이므로 `6→5→4→3→2→8→9→119...`처럼 앞뒤가 바뀔 수 있습니다. 번역 후에는 대사 순서대로 새 누적 경계를 계산한 뒤, 원본 슬롯별 대상 관계에 따라 해당 값을 다시 기록합니다.

같은 누적값을 여러 슬롯이 참조하거나 빈 대사 때문에 경계값이 중복될 수 있습니다. 따라서 숫자가 같다는 이유만으로 파일 전체를 치환하면 안 됩니다. `슬롯 위치→대상 경계` 대응표, 무수정 왕복, 한 대사 확장 시험이 확인될 때까지 `CONDITIONAL`로 판정합니다.

사용자가 포인트 시작 주소를 몰라도 됩니다. 첫 대사 주소를 확정한 뒤 바로 앞에서 4바이트씩 역방향으로 읽으며 원본 누적 경계 또는 허용된 0값이 연속되는 구간을 찾습니다. `SRVC_35.bin`에서는 첫 대사 `0x2B08`에서 역추적하여 `0x2270`의 비일치 값 `0x00000003`에서 멈추므로 포인트 시작을 `0x2274`로 자동 산출합니다. 다만 앞쪽 일반 정수가 우연히 누적값과 같아 경계가 모호하면 주소를 추측하지 않고 `NOT YET ESTABLISHED`로 보고합니다.

## 설치

Codex에 다음과 같이 요청합니다.

```text
$skill-installer를 사용해 이 스킬을 설치해 주세요:
https://github.com/MINGS-KO-PATCH/korean-game-localization-skills/tree/main/skills/game-dialogue-expansion
```

명령줄 설치 도구를 사용할 경우:

```text
install-skill-from-github.py --repo MINGS-KO-PATCH/korean-game-localization-skills --path skills/game-dialogue-expansion
```

설치된 스킬은 다음 대화부터 사용할 수 있습니다.

## 사용 예시


```text

```

```text
$game-dialogue-expansion을 사용해 추출기와 재삽입기를 검토하고, 원본 ID·빈 엔트리·제어코드·정렬·상위 컨테이너가 보존되는지 확인해 주세요.
```

## 안전 원칙

- 원본 ROM·디스크 이미지와 권한 없는 제3자 자산은 저장소에 포함하지 않습니다.
- 디코딩 성공을 대사 모집단 완성이나 확장 가능성으로 간주하지 않습니다.
- 원본 ID, 빈 엔트리, 중복 포인터, 제어코드, 헤더와 메타데이터를 임의로 정규화하지 않습니다.
- 오프셋은 수정본에 델타를 반복 적용하지 않고 최종 직렬화 결과와 원본 좌표에서 다시 계산합니다.
- 정적 검증과 실제 에뮬레이터 검증의 범위를 구분합니다.

## 저장소 권한

누구나 읽기·설치·포크·변경 제안(PR)을 할 수 있습니다. 원본 저장소에 직접 쓰는 권한은 소유자 또는 소유자가 명시적으로 권한을 부여한 협업자에게만 있습니다.

## 향후 확장

확인된 사례는 바로 일반 규칙으로 만들지 않습니다. 바이트 레이아웃, 좌표 기준, 재계산 공식, 예외, 무수정 왕복과 실패 경로가 확인되면 새 Type 또는 기존 Type의 변형으로 추가합니다. 특정 게임의 주소와 수치는 사례 근거로 남기고 다른 게임에는 재검증 없이 전용하지 않습니다.
